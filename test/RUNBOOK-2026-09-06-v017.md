## What this sitting is for

`diffDomainGrants()` now computes `toRequest` from domains this change ADDED,
intersected with what is not granted. Through v0.1.6 it was every ungranted
domain in the surviving set. The selftest proves the set arithmetic; it cannot
prove what Chrome does with the result, and every row below is a wire or dialog
question.

**The load-bearing row is P1.** Option A was ruled on the argument that the
clickable chip is a complete in-app recovery path for a denied domain. If P1
falsifies, the ruling is wrong and the correct output is to revert to option B,
not to reinterpret P1.

## Rig

Two Chrome profiles, per the standing rig. `hw-test` for the unpacked

Hostnames `g1.test` – `g9.test`, none reused from sittings A–F. None resolve

correction — the panel reports effective access, `getAll()` reports the literal

## Part A — the recovery path (P1, P2)

**P1. Deny the dialog for a never-approved host, then click its gray chip, and
a dialog appears.**
Procedure: create a profile on `g1.test`, deny the dialog at save. Confirm
`getAll().origins` contains no `g1.test` pattern. Click the gray `g1.test`
chip on the card.
*Falsification: no dialog appears, or the chip is not clickable, or the chip
is absent.* Any of those means a denied domain has NO in-app recovery under
v0.1.7, which is FINDING-002 reintroduced by this release's own fix. **STOP the
release.** Revert `grants.js` to the v0.1.6 line, rule option B instead, and
record P1's wording unchanged.

**P2. Approving that chip grants ONE domain, not the set.**
Procedure: with `g1.test` still denied and profiles on `g2.test` and `g3.test`
also ungranted, approve the `g1.test` chip's dialog. Read `getAll()`.
Expected: `*://g1.test/*` and `*://*.g1.test/*`, and nothing for g2 or g3.
*Falsification: any g2 or g3 pattern appears.* That is FINDING-028 living in
the chip path as well as the reconcile path, which the fix does not touch.

## Part B — the finding itself (P3, P4, P5)

**P3. Deleting a profile with all grants denied produces NO dialog.**
Procedure: OBS-E5's shape exactly. Five profiles on `g4.test` – `g8.test`, every
dialog denied, `getAll().origins` empty of managed patterns. Status line reads
`5 profiles · 0/5 domains granted`. Delete the first profile and confirm.
Expected: no dialog, status line `4 profiles · 0/4`.
*Falsification: any dialog appears.* The fix does not work and the release does
not ship.

**P4. The status line does not move on that delete.**
Recorded separately from P3 because OBS-F2's signature was a status-line jump
(`0/5` to `2/5`) from a single approval. Expected `0/4` after, i.e. the
denominator falls and the numerator stays at zero.
*Falsification: the numerator rises without a dialog.* That would mean a silent
re-grant on a delete, which sitting C says can only happen for an origin
already approved in this browser profile — so it would also mean the rig is
contaminated and the row must be re-run in a clean profile.

**P5. An edit to one profile does not re-request another profile's ungranted
domain.**
FINDING-024's shape without needing a legacy install. Profiles on `g4.test`
(denied) and `g5.test` (granted). Edit the `g5.test` profile's header value —
domains untouched — and save.
*Falsification: a dialog naming `g4.test` appears.*

## Part C — the legacy path, and it may not be runnable (P6, P7)

Requires an install that granted under v0.1.3, i.e. the `hw-clean` profile with
v0.1.3 loaded from the release ZIP first. Sitting E's Phase C precondition check
is the model: **establish that a legacy-only grant actually exists before
taking either row.** Without that check P7 records as passed against a fix that
does nothing.

**P6. On upgrade, a legacy-only domain still renders as a migrating chip with
its underline and its notice.**
Unchanged behaviour; this is a regression row, not a new claim.

**P7. Saving an unrelated profile does NOT re-request the legacy domain, and
clicking its chip DOES.**
This is the pair that makes the migration notice true. The pre-0.1.7 build
re-requested every legacy domain on any save.
*Falsification of the first half: a dialog naming the legacy domain appears on
an unrelated save.* *Falsification of the second: the chip does not complete
the upgrade, in which case the migration has no path at all and P1's verdict
was too narrow.*

**If Part C cannot be run**, say so in EVIDENCE.md and name what is unclosed —
do not fold it into Part B and do not describe the release as legacy-verified.
Sitting D's store-CRX row is the precedent: a row argued to be unrunnable turned
out to cost ten minutes.
