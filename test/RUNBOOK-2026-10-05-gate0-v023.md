## Facts the predictions depend on, read from the v0.2.3 source

- **A fresh install starts with the master toggle OFF.** `hw:enabled` is
  read as `=== true`, and a new install has no such key. So a fresh install
  reads `paused`, and "apply" in this row includes switching the toggle ON
  (`#master-toggle`, label `#toggle-state`). Read at the tag in
  `getEnabled()` (`popup.js:163`) and `stored.js:72`.
- **`configRevision([], false)` is `69709b56` in v0.2.3**, as in v0.2.2.
  Computed in Node from the tag's `lib/status.js`, and read back from
  `hw:sync` after loading the tag's `extension/` in Chromium 141 (below).
- **The status strings did not change in s3:** `git diff v0.2.2 v0.2.3 --
  extension/lib/status.js` is empty. The footer still says `applying`
  (UI-04 targets v0.2.4).
- **A draft for a profile not saved yet is stored under the key `new`, and
  has no card.** `init()` always shows the list, so a reopened popup shows
  the empty list with no marker. The draft is restored only when **Add
  profile** is pressed: `openEditor(null)` reads `draftFor(drafts, null)`
  and shows *Showing unsaved changes.* (`popup.js:879`, `lib/draft.js`
  `draftKeyFor`, `draftFor`). Its `version` is 2 and its `baseDigest` is
  `null` (`formToDraft`, `DRAFT_VERSION`).
- **Save on a new profile takes no base check** (`editingProfileId ===
  null`), writes `hw:profiles`, ends the draft session, which drops the
  `new` draft, and then requests the grant (`saveProfile`, `popup.js:1058`).
- **Chrome rewrites `manifest.json` at install.** The sandboxed unpacker
  parses the manifest, adds the public key as `key`, and writes it back
  re-serialized (`extensions/browser/sandboxed_unpacker.cc`,
  `RewriteManifestFile`); this is from memory of the Chromium source, not
  read in this session. So the installed manifest's bytes are not expected
  to equal the store's (sha256 `f3bd68f6…`, the tag's manifest plus an
  `update_url` line), and S-4m compares content.
