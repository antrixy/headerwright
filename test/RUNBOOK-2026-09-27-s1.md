## Two decisions, made 2026-09-27 before any prediction was written

**1. AR-05's browser evidence is a fault injected from the popup's DevTools
console. The build under test is unchanged.** `chrome.storage.local.get` is
replaced, in the popup's own page, by a version that rejects only for the key
`"hw:sync"`. Only the render reads that key with nothing to catch it
(`getSyncState()`, `popup.js:177`). The delete path's `getProfiles()` and
`setProfiles()` and all of `reconcileGrants()` never read it. No file in
`extension/` changes. Closing the popup discards the replacement.

This is evidence of the wiring under a synthetic fault, not of a render failure
that occurred naturally. That is stated here so the ledger row cannot later be
read as more than it is. The alternatives were weaker. Counting the test-suite
evidence as the row's evidence would make `verified` mean something new for one
row, and it says nothing about the wiring FINDING-046 records as unguarded. A
built-in forced failure changes the build under test.

**2. The `api-staging` demo profile on `api.example.com` in `hw-test` is kept
and consumed as AR-05's subject.** It is a granted domain referenced by one
profile, which is exactly what a revoke test needs, and it needs no permission
dialog to set up. The store screenshot it was kept for gets redone when s4
changes the popup anyway. It does not survive this sitting.

A row is only evidence against the builds it would fail on. The counterfactual

**Two rows NEXT.md names cannot fail on PRE, and are run anyway, labelled.**

- *A double-click on Delete's confirm gives one write.* PRE's `confirmDelete`
  already calls `hideDeleteConfirm()`, which nulls `pendingDeleteId`, before
  its first await (`52071a6` `popup.js:734–739`). A second click returns early
  on PRE too. Row D4.
- *A double-click on Save gives one write*, with a real mouse. A normal save
  finishes, and the view switches back to the list, well inside a double-click
  gap, so the second click never lands on Save. Row D2.

**Row D1 is the discriminating form of the Save row.** Two `click()` calls in
one task land before the first save's first await, so the second click finds
the gate busy. PRE and M-nogate give two writes. **Row D3 is the only row that
reaches the gate's refusal itself.** `disabled` stops a click before any
listener runs, but grant chips are not disabled, and `click()` ignores
`pointer-events: none`.

**The "slow save" prep question is answered by pausing, not slowing.** A
DevTools breakpoint inside `saveProfile` holds the gate busy for as long as
needed, with no change to the build. While the page is paused, input is not
delivered, so paused rows read state and never click. The click rows (D1–D3)
run unpaused.
