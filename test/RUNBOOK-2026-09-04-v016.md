## 1. What is different about this sitting, and why it is shorter

**Nothing in v0.1.6 touches the wire.** All three items are display: layout
containment (FINDING-022), a wording change carrying a distinction out of an
unreachable tooltip (FINDING-023), and two refusal messages that no longer
claim things that are false (FINDING-026). No rule is built differently, no
grant is requested differently, no header changes.

So there is **no echo server and no `/etc/hosts` work in this sitting**, and
that is a deliberate reading, not an oversight. Parts 1 and 13 are the wire
regression, and they are unchanged code — the only reason to re-run them is if
something in this sitting suggests otherwise.

**The oracle is the screen, and it is weaker than a wire reading.** A wire row
either shows the header or does not. A layout row is a judgement about whether
something is visible, which is exactly the kind of oracle this project distrusts
— so the rows below are written to be answerable yes/no at a stated profile
count, not "does it look better".

**What the selftest already covers, so the sitting does not have to.** The
suite is at 272 checks and the FINDING-026 message contracts are pinned there
(which header, which profile, no claim about applying, the overlap stated once,
no self-terminating punctuation), verified by a nineteen-mutant pass in which
every mutant died. The messages therefore do not need to be *read* in the
browser to know what they say. What the browser adds is that they FIT and
RENDER — P8 in sitting D was wrong precisely because reading a string is not
seeing it.

## 2. Preconditions

**One Chrome profile is enough.** No wire readings means no risk of two builds
registering competing DNR rules, which is what forced the two-profile split in
sitting D.

**It must have no approval history for the hostnames used**, for the same
reason as always: a primed origin grants silently and reads identically to a
legitimate dialog-less pass. Any fresh profile does.

**The domains do not have to resolve.** Every row below is about what the popup
displays, and the popup renders profiles and chips whether or not the host
exists. Use throwaway names — `p1.test` … `p8.test`. **Do not reuse a hostname
from sittings A–D.**

**One row needs a second window size.** P4 is the small-display falsifier and
needs Chrome on a display, or in a window arrangement, short enough that the
popup is sized below 600px. If that cannot be produced, record P4 as NOT
REACHED — do not mark it right.

**Confirm before starting, on the tagged tree:**

### P13 — the one I most expect to be interesting

**Whether pinning has made the confirmations worse.** P7 predicts the delete
confirmation lands below the fold at 8 profiles. Before v0.1.6 the popup grew
until Chrome's 600px ceiling and then scrolled bodily, so a confirmation could
also be off-screen — the failure is not new. What IS new is that the visible
region is now permanently bounded, so the confirmation is off-screen *sooner*,
and the pinned footer means there is no longer any visual cue that the popup
continues below.

Confidence: medium that P7 is confirmed. Genuinely unsure whether it matters.

**Record it explicitly either way, and do not fix it in this sitting.** If
confirmed, it is a candidate finding for the v0.2.0 redesign, where the card
shape and the confirmation placement are decided together. A defect found
during a run is recorded and left alone; patching it mid-sitting invalidates
every row after it. The obvious one-line fix — `scrollIntoView()` on the
confirmation — is NEW BEHAVIOUR by the patch policy and would be a fourth
recorded deviation, so it does not get made casually at the end of a sitting.

### P14 — the tooltip question, deliberately not a fix

FINDING-023's root cause is not established: nothing says whether `title` fails
to render because of Chrome's handling of extension popups or because of
something in the markup. **v0.1.6 does not attempt to fix it.** It removes the
dependency instead — the migration distinction now lives in the notice text.

C2 is a two-minute DISCRIMINATOR, and it is worth running because it is cheap
and it decides whether a future fix exists at all:

- hover a **granted** chip — a `<span>` with a `title`
- hover an **ungranted** chip — a `<button>` with a `title`
- hover the **master toggle** — a `<label>` with a `title`, shipped since v0.1.0
- hover the **status line** after a failed sync — a `<footer>` with a `title`

**If NO tooltip appears anywhere in the popup**, it is Chrome or the
environment, FINDING-023 is not a HeaderWright defect, and the entry should be
reclassified rather than carried. **If some appear and the chips do not**, it is
the markup, and there is a real fix to scope. Either answer closes a question
that has been open since sitting D.

Prediction: no tooltip appears anywhere. Confidence: low. This is the one I
would most like to be wrong about, because a markup cause is fixable.
