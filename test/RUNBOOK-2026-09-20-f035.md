## The three candidate mechanisms

Both existing sightings share a positional confound: `set` at
`responseHeaders[0]`, `remove` at `responseHeaders[1]`, index 0 applied and
index 1 did not. No response-side `remove` has ever been observed at index 0,
and no response entry other than index 0 has ever been observed applying.

| | Claim |
| --- | --- |
| **M1** | Response-side `remove` is not applied. (FINDING-035 as originally written.) |
| **M2** | Only the FIRST entry of a rule's `responseHeaders` array is applied. |
| **M3** | Within-rule precedence state is tracked per REQUEST rather than per HEADER, so any `set` blocks every later response modification in the same rule. |

Chrome's documented precedence explains C9 sequence 4 (same header, `set` then
`remove` — a disallowed combination) and does NOT explain C8 (different
headers, which MDN states apply independently). So either the two sightings
have different causes, or Chromium diverges from its documentation on the
per-header scoping. These rows do not need that question settled in advance.

## Disposition note — why the mechanism decides the ruling

Under **M1**, deferring `remove` to v0.2.1 with the validator refusing it is a
clean ship: `set` works, `remove` is refused with a reason on screen, v0.2.0
ships one response operation instead of two. `SCOPE.md` needs the same move
`append` already got, dated under the document's own change rule.

Under **M2 or M3**, that escape does not exist. A validator refusing `remove`
would ship a `set` that silently fails in any profile with two response
entries, behind a refusal message that says nothing about it. The honest
options narrow to one response entry per rule enforced by the validator, or
splitting response entries across rules with distinct priorities, or deferring
response headers wholesale. **Do not write the disposition entry before E2 is
read.**
