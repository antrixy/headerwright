## The three candidate mechanisms

Both existing sightings share a positional confound: `set` at
`responseHeaders[0]`, `remove` at `responseHeaders[1]`, index 0 applied and
index 1 did not. No response-side `remove` has ever been observed at index 0,
and no response entry other than index 0 has ever been observed applying.

| | Claim |
| --- | --- |
| **M1** | Response-side `remove` is not applied. (FINDING-035 as originally written.) |
| **M2** | Only the FIRST entry of a rule's `responseHeaders` array is applied. |
| **M3** | Within-rule precedence state is tracked per REQUEST rather than per HEADER, so any `set` blocks every later response modification in the same rule. |

Chrome's documented precedence explains C9 sequence 4 (same header, `set` then
`remove` — a disallowed combination) and does NOT explain C8 (different
headers, which MDN states apply independently). So either the two sightings
have different causes, or Chromium diverges from its documentation on the
per-header scoping. These rows do not need that question settled in advance.

## Results — what the three reads establish

| rule shape (one rule, one `responseHeaders` array) | outcome |
| --- | --- |
| `set` A, `set` B — E2 | both applied |
| `remove` A alone — E1 | applied |
| **`remove` A, then `set` B — E3** | **both applied** |
| **`set` B, then `remove` A — C8** | **`remove` ignored** |
| **`set` A, then `remove` A — C9 seq 4** | **`remove` ignored** |

**M1′ (post-hoc): a `set` earlier in a rule's `responseHeaders` array
suppresses every later `remove` in that same array, including on a DIFFERENT
header. Put the `remove` first and both apply.**

It is not `remove` being broken (E1, E3). It is not position (E2, E3, both of
which apply an entry at index 1). It is not a per-request block on all later
modification (E3 applies a `set` at index 1 after a `remove` at index 0).

Two properties worth stating separately:

**The suppression is not per-header.** C8's two entries touch different headers
and the later `remove` was still suppressed. Chrome's own reference and MDN
both state that modifyHeaders actions apply independently when they touch
different headers. This is a Chromium divergence from documented behaviour, and
it is reportable: Chrome 153.0.8010.48, macOS 26.5.2, arm64, dynamic rules, one
extension, single rule, priority 1.

**The suppression is asymmetric, which is what makes it a defect rather than a
precedence rule.** Chrome's documented precedence governs ordering BETWEEN
rules, where a consistent first-wins would be coherent. Here, inside one array,
`remove`-then-`set` yields both and `set`-then-`remove` yields one. Same two
operations, same two headers, different outcome by array order alone.

**M1′ WAS NOT PREREGISTERED.** It was formulated between the E2 and E1 reads,
after M2 and M3 had fallen. Two of the three rows matched no registered
prediction. The mechanism fits five observations across two sittings and two
tree states, which is not nothing — but by this project's own standard a
hypothesis written after the data is believed, not established. E4 below exists
to fix that and should be run before any fix is written.

## Disposition note — why the mechanism decides the ruling

Under **M1**, deferring `remove` to v0.2.1 with the validator refusing it is a
clean ship: `set` works, `remove` is refused with a reason on screen, v0.2.0
ships one response operation instead of two. `SCOPE.md` needs the same move
`append` already got, dated under the document's own change rule.

Under **M2 or M3**, that escape does not exist. A validator refusing `remove`
would ship a `set` that silently fails in any profile with two response
entries, behind a refusal message that says nothing about it. The honest
options narrow to one response entry per rule enforced by the validator, or
splitting response entries across rules with distinct priorities, or deferring
response headers wholesale. **Do not write the disposition entry before E2 is
read.**

> **UPDATE 2026-09-20, after the reads.** Neither branch above applies, because
> the mechanism is M1′ and neither M1 nor M2/M3 survived.
>
> **Refusing `remove` in the validator is now the WRONG call** — `remove` works,
> both alone and ahead of a `set`. The candidate fix is that `buildRules()`
> emits response `remove` entries ahead of `set` entries within
> `responseHeaders`: cheap, pure, testable in `rules.js`, no UI change.
>
> **That fix is not free, and it is a RULING rather than a patch.** It collides
> with the project's own claim that array order is preserved on the wire, which
> is FINDING-036's subject. Reordering behind the user's back makes `remove`
> work and makes that claim false by construction, and the popup has no reorder
> control with which a user could express a preference either way. The
> alternatives — refuse a `set`-before-`remove` array in the validator, or split
> across rules with distinct priorities — keep the order claim and cost either
> expressiveness or rule budget.
>
> **035 and 036 are probably ONE mechanism.** 036's request-side sighting is
> `append` then `set` with the `set` discarded — an earlier entry suppressing a
> later one in the same array, on the request side. Do not merge the findings on
> that suspicion alone; the request-side shape has one sighting and no
> equivalent of E1/E3 behind it. A request-side E1/E3 pair would settle it.
>
> Sequence from here: run E4, then rule on the fix in `decisions.md`, then
> patch. **The v0.2.0 tag stays blocked** until the ruling exists, and
> separately until the stale manifest description is dealt with — the shipped
> 0.2.0 manifest still reads "Modify HTTP Request Headers" / "Set, append, and
> remove HTTP request headers by profile", which is user-visible in
> `chrome://extensions` and in any store listing, and is wrong twice over on a
> response-header release.
