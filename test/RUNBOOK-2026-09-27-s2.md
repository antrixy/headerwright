## What AR-01b claims, and how each row can fail

s2 binds an edit to the profile the editor was opened on. When Save runs, the
stored target must still have the same `sha256:profile-v1:` digest.

- If the target **changed**, Save writes nothing, says `Not saved: this
  profile was changed after you opened it…`, keeps the form, and shows the
  draft notice that holds **Revert to saved**.
- If the target **vanished**, Save writes nothing and says `Not saved: this
  profile was deleted after you opened it…`.
- A change to a **different** profile does not refuse the edit.
- Revert to saved loads the current version, takes the base again, and
  clears the error.

Another writer is simulated from the popup's own DevTools console. It
rewrites `hw:profiles` in `chrome.storage.local` while the editor is open.
That is the only way to change storage underneath an open editor today (AR-07b's
trigger). A storage change re-renders only the hidden list
(`scheduleRerender` → `renderList`). It does not touch the editor, its form or
its base.

| name | what it is |
| --- | --- |
| PRE | v0.2.1 (`bd4e5df`): no base check. A changed target is silently overwritten; a vanished one "saves" the unchanged set and returns to the list |
| M-scope | the check compares the whole configuration, not the target |
| M-stale-base | Revert to saved does not take the base again |
| M-noclear | Revert to saved leaves the refusal on screen |
| M-nonotice | a "changed" refusal does not show the draft notice |

Row N fails on M-scope. Row V fails on PRE. Row C fails on PRE, M-stale-base,
M-noclear and M-nonotice.
