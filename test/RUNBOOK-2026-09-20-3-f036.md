## Why this sitting exists

FINDING-036 is the last unverified claim standing between this project and a
v0.2.0 tag decision, and **it is in exactly the epistemic position C8 was in
before it fell.**

Its single sighting is C9 sequence 2, 2026-09-19: `requestHeaders[1] =
{X-Forwarded-For, append, bravo}` and `requestHeaders[2] = {X-Forwarded-For,
set, alpha}` produced `bravo` on the wire, where `alpha` was predicted. The
entry states that the setup was verified with `getDynamicRules()` before the
read, "which is what makes the result trustworthy".

**C8 said the same thing, and C8 was wrong.** Both were built in the same
sitting, in the same popup, by the same hand, and the popup has since been
shown to hold two defects that each make a claimed verification unreliable:

- **FINDING-040** — an operation name typed into the value field yields a legal
  entry that silently does something else.
- **FINDING-042** — an in-progress edit discarded when the popup loses focus,
  which is what opening the service worker console does. FIXED and verified
  2026-09-20, but it was live on 09-19.

**042 explains C9 sequence 2 exactly, with no Chrome anomaly required.** If the
second entry never reached storage, only `append bravo` applied, and the wire
reads `bravo`. That is the observed result. It requires the `getDynamicRules()`
claim to be false — which is precisely what C8 turned out to require.

**This is not a claim that 036 is wrong.** Unlike C8, its mechanism is
independently plausible: Chrome's documented precedence says that once a rule
has appended to a header, `set` and `remove` are treated differently, and
`ROADMAP-v0.2plus.md` §v0.2.1 already records it. 036 may well be real. It has
simply never been read twice, and everything else from that sitting that was
read twice did not survive.
