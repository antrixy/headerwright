**Written 2026-09-01, BEFORE the browser was opened.** Predictions in section 4

Target: enough wire evidence to tag v0.1.5. Estimated 30–40 minutes.

## 1. Why phase A comes first, and why it cannot be rescheduled

**The 0.1.4 store build is a consumable fixture and the window closes at
publish.** A colliding pair can only be *created* on a build that permits it.
Once 0.1.5 is live, `saveProfile()` refuses, and no store install will ever
construct one again. The repo ZIP is not a substitute — Chrome cannot
auto-update an unpacked load, and Chrome's update path is the only thing the
fixture exists to observe.

So phase A is built, verified, and then LEFT ALONE. Nothing else in this
sitting touches that profile.

Phase A also re-takes OBS-C10 on a genuine store artifact for free, which
retires the provenance question about the v0.1.5 before-state.

**SMOKE.md Part 13 lists steps 5 and 6 in the wrong order.** Step 5 ends by

**Step 4 is also improved over what SMOKE.md says.** As written it has you
write a colliding pair straight into storage, which leaves both domains

not by the refusal. The row proves nothing. Instead:

1. Create two profiles on `s1.test` and `sub.s1.test` with **different** header

2. Grant both. Confirm **both headers apply** on the wire. This is the before.
3. From the service worker console, edit `hw:profiles` so both header names are
   **identical**. Reload the extension.
4. Observe.

Same profiles, same grants, one field changed. That is a real before/after
rather than an absence.

### P15 — the one I most expect to be interesting

**Export of a colliding configuration SUCCEEDS, and the resulting file cannot
be re-imported.** `serializeProfiles()` does not validate; `parseProfilesFile()`
now refuses. So v0.1.5 can produce a file it will not accept.

Confidence: high that it happens. Genuinely unsure whether it is acceptable.

It matters because a 0.1.4 user who upgrades into a collision and exports —
the natural move, and the one the export button invites — gets a file that is
now unloadable. It is recoverable (edit the file, or fix it in the UI), and
the refusal message names the header and the other profile. But "identical
profile sets always serialize to identical bytes" was a contract about
round-tripping, and a config that exports and will not import is a new
asymmetry in it.

**Record it explicitly in step 6 either way.** If confirmed, it is a candidate
FINDING-026, not something to patch mid-sitting. A defect found during a run is
recorded and left alone; fixing it mid-sitting invalidates every row after it.

## 5. Phase A — the expiring fixture (store 0.1.4)

1. New Chrome profile `hw-fixture`. Not signed in.
2. Install HeaderWright **from the Chrome Web Store**. Confirm the version
   reads 0.1.4 and record the extension id — it should be the store id
   `ooapgilielelobkkcdlnkenkflbnnmhi`, not a path-derived one. **If it is not
   the store id, stop: the wrong build is loaded.**
3. Profile "Fix1" on `f1.test`, header `X-Fix: A`. Save, grant.
4. Profile "Fix2" on `sub.f1.test`, header `X-Fix: B`. Save, grant.
   Record the creation order and both ids — P2 turns on it.
5. Toggle ON. Browse `http://sub.f1.test:8080/`. Record the exact response
   headers.
6. **STOP.** Do not delete, edit, export, or open the popup again. Do not
   uninstall. Leave the profile closed until after 0.1.5 is live on the store.

Post-publish (a separate sitting, days later — store review takes time): open
`hw-fixture`, force an update from `chrome://extensions`, and record whether
both profiles are now marked and neither header applies. That is the only
observation of the build-path refusal reaching an install Chrome *updated*
rather than one that was reloaded by hand.
